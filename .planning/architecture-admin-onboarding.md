## Component Breakdown

### Feature 1: Token-gated registration
- **Files**: `apps/api/src/config.ts`, `apps/api/src/infra/auth/session.ts`, `apps/api/src/infra/http/routes/register.ts` (new), `apps/api/src/infra/http/routes/auth.ts`, `apps/api/src/infra/http/server.ts`, `apps/api/prisma/schema.prisma` + migration, `apps/web/src/pages/RegisterPage/*` (new), `apps/web/src/router.tsx`, `apps/web/src/pages/LoginPage/LoginPage.tsx`, `apps/web/src/api/hooks.ts`, `apps/web/src/context/strings/de.ts`.
- **Dependencies**: none new. Reuses `safeEquals` (already in `session.ts`), `hashPassword` (`infra/auth/password.ts`), `DEFAULT_CONFIG`/`parseConfig` (`@haushaltsauktion/shared`), `@fastify/rate-limit` (already registered).
- **Complexity**: medium — the only backend logic in this whole PRD, and it touches a shared helper (`issueSession`) used by an existing, security-sensitive endpoint (`/auth/login`), so the refactor must not change login's behavior.

### Feature 2: Member admin panel
- **Files**: `apps/web/src/pages/AdminPage/AdminPage.tsx`, `AdminPage.module.css`, `apps/web/src/api/hooks.ts`, `apps/web/src/api/types.ts`, `apps/web/src/context/strings/de.ts`.
- **Dependencies**: none new. Zero backend changes — `GET/POST /admin/members`, `PATCH /admin/members/:id`, `PUT /admin/members/:id/restrictions` already exist and are already covered by existing backend tests.
- **Complexity**: medium — mostly form/list plumbing, but restrictions editing (category exclusions, task exclusions, absence date ranges) has real shape (three sub-lists in one PUT body).

### Feature 3: Task-definition + category admin panel
- **Files**: same files as Feature 2 (same `AdminPage.tsx`/`hooks.ts`/`de.ts` — sequenced after Feature 2 to avoid the same file changing in two phases at once).
- **Dependencies**: none new. Zero backend changes.
- **Complexity**: medium — the recurrence sub-form (type + conditional interval/weekdays/dayOfMonth/timeOfDay/dueOffsetMinutes fields, per `RecurrenceBody` in `admin.ts`) is the fiddliest part; category CRUD is trivial by comparison.

## Data Model

### AuditAction (enum, modified)
- Add one value: `HOUSEHOLD_REGISTERED`. Requires a Prisma migration (`npx prisma migrate dev --name add_household_registered_audit_action` inside `apps/api`, run against the dev DB per this project's existing `db:migrate:dev` convention).

No other schema changes. `Household`, `HouseholdConfiguration`, `User`, `HouseholdMember`, `TaskDefinition`, `TaskCategory` are all consumed as-is by the new endpoint/UI, exactly as `create-admin.ts` and the existing `admin.ts` routes already do.

## Key Decisions

### Session issuance: extract `issueSession` vs. duplicate the login block
- **Chosen**: extract an `issueSession(deps, env, { userId, householdId, ipAddress, userAgent }): Promise<{ sessionId: string; rawSession: string; rawCsrf: string }>` helper into `apps/api/src/infra/auth/session.ts` (the module that already owns `generateToken`/`hashToken`/`csrfTokenFor`/`safeEquals`/`cookieOptions` — this is where session lifecycle logic already lives, not `auth.ts`, which is route handlers). `auth.ts`'s login handler is rewritten to call it and then do only its login-specific work (audit event, cookie set from the returned `rawSession`). `register.ts` calls the same helper.
- **Rejected**: duplicate the ~20-line session-creation block into `register.ts`. Two copies of security-sensitive session-issuance code (session row + CSRF derivation + placeholder-hash timing window) will drift the first time either one is touched — the exact failure mode the codebase's `safeEquals`/`burnPasswordTime` helpers already exist to avoid elsewhere.

### Setup-token verification
- **Chosen**: reuse the existing `safeEquals(a, b)` from `session.ts` — it already does length-checked `timingSafeEqual`, is already imported by nothing outside `auth.ts` today but is exported and general-purpose. `register.ts` calls `safeEquals(submittedToken, env.SETUP_TOKEN)` only when `env.SETUP_TOKEN` is defined; if undefined, the route is never registered (see below), so there is no comparison to make.
- **Rejected**: a fresh `crypto.timingSafeEqual` call in `register.ts`. `safeEquals` already exists, is already exercised by `auth.ts`, and duplicating it would be the same drift risk as the session block above.

### Disabling `/register` when `SETUP_TOKEN` is unset
- **Chosen**: `server.ts` only calls `registerRegisterRoutes(api, deps, env)` when `env.SETUP_TOKEN` is defined (`typeof env.SETUP_TOKEN === 'string'`) — the route simply doesn't exist on the Fastify instance, so Fastify's own 404 handler answers, matching the PRD's "endpoint responds 404" end condition without a query-time branch that could be gotten wrong.
- **Rejected**: always register the route, return 403 inside the handler when the token is unset. Works, but leaves a discoverable route (Fastify's route introspection, error messages) advertising a disabled admin-creation endpoint — the PRD's product intent ("effectively doesn't exist") is better served by not registering it.

### `TaskDefinition`/`TaskCategory`/`Member` list refresh strategy in the new hooks
- **Chosen**: mirror `useAdminConfig`/`useSaveConfig` exactly — one `useQuery` per list endpoint, one `useMutation` per write endpoint, each mutation's `onSuccess` calls `qc.invalidateQueries` on the relevant list's query key. No optimistic updates.
- **Rejected**: optimistic updates (mutate the cache directly, roll back on error). The existing admin hooks in this codebase don't do this anywhere (`useSaveConfig`, `useRunSweep` both just invalidate), and admin actions here are low-frequency enough that a refetch round-trip is imperceptible — optimism would be new complexity with no user-facing benefit.

### AdminPage structure: two new `<section>`s vs. a new sub-router/tabs
- **Chosen**: two more `<section className={styles.section}>` blocks appended after the existing five, using local `useState` per section (mirrors the existing `draft`/`message` local-state pattern already in the file).
- **Rejected**: `@radix-ui/react-tabs` (already a dependency, used elsewhere per `package.json`) to split AdminPage into tabs. Tempting given it's already a dependency, but `AdminPage.tsx` today is a single flat scroll with no navigation chrome at all — introducing tabs here would be a new UI pattern for this one page while every other page in the app (Dashboard, TaskList, History, Ledger) is also a single flat scroll. Consistency with the rest of the app wins over the marginal ergonomics of tabs on what is likely to stay a rarely-visited page.

### Phase 1: Registration backend
- **Goal**: `POST /register` exists, is token-gated, atomically creates Household+Config+User+Member(ADMIN), audits it, and logs the caller in — with `issueSession` extracted and reused by both it and the existing login handler.
- **Files**: `apps/api/src/config.ts`, `apps/api/src/infra/auth/session.ts`, `apps/api/src/infra/http/routes/auth.ts`, `apps/api/src/infra/http/routes/register.ts` (new), `apps/api/src/infra/http/server.ts`, `apps/api/prisma/schema.prisma` + migration.
- **Dependencies**: Phase 0.
- **End Conditions**:
  - [ ] `SETUP_TOKEN` unset in test env → `POST /api/register` returns 404.
  - [ ] `SETUP_TOKEN` set + correct token + new email → 201/200 with session cookie set, response shape matching `/auth/login`'s (`user`, `member`, `household`, `csrfToken`); a `Household`, `HouseholdConfiguration` v1, `User`, `HouseholdMember(ADMIN)` row each exist afterward; one `AuditEvent` with action `HOUSEHOLD_REGISTERED` exists.
  - [ ] Wrong token → 403, zero new DB rows in any of the four tables, response time not distinguishably different from the correct-token-wrong-email case (existing `burnPasswordTime`-style test convention if one exists for `/auth/login`, otherwise a explicit assertion that the token check runs before any early return).
  - [ ] Duplicate email → same conflict response shape as `POST /admin/members`'s duplicate-email case.
  - [ ] Rate limit trips at 6th request within 5 minutes from one IP, matching `/auth/login`'s existing limiter shape.
  - [ ] Existing `/auth/login` integration tests still pass unmodified against the refactored `issueSession`-based handler (this is the regression check that the extraction didn't change login behavior).
  - [ ] `npm run typecheck` — 0 new errors vs. Phase 0 baseline.
  - [ ] `npm run test` — 0 new failures vs. Phase 0 baseline; new tests added for all conditions above.

## Phase Dependency Graph

```
Phase 0 (Baseline)
  ├─→ Phase 1 (Registration backend) ─→ Phase 2 (Registration frontend) ─┐
  └─→ Phase 3 (Member admin panel) ─→ Phase 4 (Task-definition panel) ───┤
                                                                          ├─→ Phase 5 (Docs)
```

Phases 1→2 and 3→4 are each a serial pair (frontend needs its backend; Phase 4 is sequenced after Phase 3 to avoid two phases editing `AdminPage.tsx` concurrently). The {1,2} pair and the {3,4} pair touch disjoint files until Phase 5 and could run as parallel Fleet waves if desired — Archon may run them serially instead given the small overall size; either is correct.

## Risk Register

1. **`issueSession` extraction subtly changes `/auth/login` behavior** (e.g. cookie flags, CSRF derivation order, audit-event timing) — mitigated by Phase 1's explicit end condition that all existing `/auth/login` tests pass unmodified against the refactored handler, plus writing the extraction as a pure lift (same statements, same order, just moved) rather than a rewrite.
2. **Regression in existing functionality** (default risk for feature-mode work) — every phase's end conditions include the typecheck/test-vs-baseline gate from Phase 0; nothing merges if it regresses either.
3. **Setup-token leakage via logs or error messages** — the token must never appear in a thrown error's message, an audit-event payload, or a log line; Phase 1's tests should assert the audit payload for `HOUSEHOLD_REGISTERED` does not include the raw token.
4. **`AdminPage.tsx` merge conflicts** if Phases 3 and 4 are parallelized despite the serial recommendation — mitigated by making Phase 4 formally depend on Phase 3 in the campaign file (not just a suggestion) so Archon/Fleet won't schedule them concurrently.
5. **Recurrence sub-form complexity underestimated** — `RecurrenceBody`'s conditional fields (interval for `EVERY_N_DAYS`, weekdays for `WEEKDAYS`, dayOfMonth for `MONTHLY`) could balloon Phase 4's scope; mitigated by explicitly scoping the recurrence editor to a plain type-select + conditional-fields form (no calendar widget) in the PRD's Out of Scope section already.

## Deployment Strategy

Not applicable — this project has no configured deployment target beyond local Docker Compose (per the existing README and `docker-compose.yml`). No new phase added for deployment; `SETUP_TOKEN` becomes one more environment variable an operator sets alongside `SESSION_SECRET`/`DATABASE_URL` when they do deploy, documented in Phase 5.
