## Component Breakdown

### Feature: Operator identity & bootstrap
- Files: `schema.prisma`, `create-operator.ts`, `operatorSession.ts`
- Dependencies: `infra/auth/password.ts` (argon2id, reused as-is)
- Complexity: low — direct mirror of `Session`/`create-admin.ts`, no new crypto primitives

### Feature: Operator auth routes & isolation
- Files: `operatorContext.ts`, `routes/operator.ts`, `server.ts`
- Dependencies: `@fastify/rate-limit` (already global), `@fastify/cookie` (already global)
- Complexity: medium — the isolation guarantee is the whole point of this feature; gets its own test file, not folded into a shared one

### Feature: Metrics aggregation
- Files: `app/operator/metrics.ts`
- Dependencies: Prisma client only (no domain/ imports — these are read-only aggregates, not business logic)
- Complexity: low — seven independent, parallelizable `count`/`aggregate` queries, no transactions, no writes

### Feature: Operator frontend shell
- Files: `operatorClient.ts`, `operatorHooks.ts`, `operatorTypes.ts`, `OperatorLoginPage.tsx`, `OperatorDashboardPage.tsx`, `router.tsx`
- Dependencies: `@tanstack/react-query` (already a dependency), no shared state with the member-facing `client.ts`/`hooks.ts`
- Complexity: low — one login form, one stat-tile grid, no charts (snapshot-only per the sharpened brief)

## Data Model

### OperatorAccount
- Fields: `id: String @id @default(cuid())`, `email: String @unique`, `passwordHash: String`, `createdAt: DateTime @default(now())`
- Relationships: has many `OperatorSession` (`onDelete: Cascade`)
- Note: deliberately has no `updatedAt`/`isActive` — v1 has no in-app operator management (Fork C), so nothing ever mutates a row after creation; add these only when an actual mutation path exists

### OperatorSession
- Fields: `id`, `operatorAccountId`, `tokenHash: String @unique`, `csrfTokenHash: String`, `createdAt`, `lastSeenAt @default(now())`, `expiresAt`, `revokedAt: DateTime?`, `ipAddress: String?`, `userAgent: String?`
- Relationships: belongs to `OperatorAccount` (`onDelete: Cascade`)
- Note: field-for-field the same shape as `Session` (schema.prisma:198-216), **minus** `activeHouseholdId` — there is structurally no field to hold a household pointer, so "an operator session accidentally scoped to a household" is not a state the type system allows

Both models sit in their own section of `schema.prisma`, clearly separated from the "identity plane" comment block that documents `User`/`Session`, with a comment explaining why they don't extend it.

## Key Decisions

### Where `requireOperator` lives: new `operatorContext.ts`, not appended to `context.ts`
- **Chosen**: a dedicated file, importing nothing from `context.ts` and exporting its own `OperatorRequestContext` type (`operatorAccountId`, `operatorSessionId`, `csrfTokenHash` — no `householdId`, no `role: MemberRole`).
- **Rejected**: adding `requireOperator`/`resolveOperatorSession` to `context.ts` alongside `requireMember`/`requireAdmin`. `context.ts`'s own header comment calls itself "the single choke point for household scoping" — mixing in a parallel identity system that is deliberately *not* household-scoped would make that claim false the moment it shipped, and every future reader of that file would have to hold two unrelated auth models in their head at once.

### Session secret: reuse `env.SESSION_SECRET` for the operator CSRF derivation
- **Chosen**: `csrfTokenFor`-style HMAC keyed by the same `SESSION_SECRET`, applied to `OperatorSession.id` instead of `Session.id`.
- **Rejected**: a new `OPERATOR_SESSION_SECRET` env var. `OperatorSession.id` and `Session.id` are drawn from disjoint cuid sequences in separate tables, so there's no cross-derivation collision to guard against, and CLAUDE.md §37 ("betreibbar für eine Familie ohne eigenen Systemadministrator") argues against growing the required-env-var list for a feature the family itself never touches.

### Metrics module shape: one function per metric, composed by an orchestrator
- **Chosen**: `computeOperatorMetrics(db, now)` in `app/operator/metrics.ts` calls out to `countActiveHouseholds`, `countActiveUsers`, `computeTaskThroughput`, etc. — each independently unit-testable, run via `Promise.all`.
- **Rejected**: one large inline query block. The codebase's existing pattern for "a checklist of independent predicates" (`assignment/candidates.ts`'s `isAbsent`, `excludedFromTask`, ...) is exactly this shape, and a single monolithic function would make it harder to unit-test "active household = 14-day task activity" in isolation from "buyout rate."

### Frontend shell: no shared `Layout.tsx`, no shared `client.ts` module state
- **Chosen**: `OperatorDashboardPage` renders its own minimal chrome; `operatorClient.ts` is a near-duplicate of `client.ts` with its own module-level `csrfToken` variable.
- **Rejected**: importing `client.ts`'s `setCsrfToken`/`api()` and just pointing at `/api/operator/*` paths. The member client's CSRF token is global module state; if an operator ever opened `/betrieb` in the same tab session as a household login (unlikely but not impossible — same browser, different path), sharing that state would let an operator-login response clobber the household session's CSRF token or vice versa. Two cookies were already kept structurally separate for exactly this class of reason (per the original brief) — the frontend should not quietly reunite them at the JS-state level.

## Build Phases

### Phase 0: Baseline
- **Goal**: record current state before touching anything, per feature-mode convention.
- **Files**: none (read-only)
- **Dependencies**: none
- **End Conditions**:
  - [ ] `npm run typecheck -w apps/api` passes on current `main`
  - [ ] `npm run typecheck -w apps/web` passes on current `main`
  - [ ] `npm test -w apps/api` passes on current `main`

### Phase 1: Data model
- **Goal**: `OperatorAccount`/`OperatorSession` exist in the schema and the database.
- **Files**: `schema.prisma`, generated migration
- **Dependencies**: Phase 0
- **End Conditions**:
  - [ ] `npx prisma validate` passes
  - [ ] `npx prisma migrate dev` generates and applies a migration cleanly against a fresh database
  - [ ] Existing test suite still passes unchanged (new tables, zero touched rows)

### Phase 2: Operator identity infrastructure
- **Goal**: an operator account can be created, and a session can be issued/verified/revoked, with zero coupling to `RequestContext`.
- **Files**: `create-operator.ts`, `operatorSession.ts`, `operatorContext.ts`
- **Dependencies**: Phase 1
- **End Conditions**:
  - [ ] `npm run create-operator` (interactive) creates an `OperatorAccount` row and prints a one-time password, following the `create-admin.ts` pattern; re-running it with a different email succeeds (Fork C)
  - [ ] `requireOperator` unit-testable in isolation: given a valid/expired/revoked/unknown token it returns the right context or throws the right `ForbiddenError`
  - [ ] `OperatorRequestContext` has no `householdId` field — a TypeScript-level guarantee, not just a runtime one

### Phase 3: Operator routes + isolation guarantee
- **Goal**: `POST /api/operator/login`, `POST /api/operator/logout`, `GET /api/operator/metrics` work end-to-end, and the cross-household isolation is proven, not assumed.
- **Files**: `metrics.ts`, `routes/operator.ts`, `server.ts`, `_fixture.ts`, `operator-isolation.test.ts`, `operator-metrics.test.ts`
- **Dependencies**: Phase 2
- **End Conditions**:
  - [ ] `GET /api/operator/metrics` returns all seven figures (total/active households, total/active-24h/active-7d users, and the five v1 metrics) computed live, matching hand-computed values against seeded fixtures
  - [ ] Regression test: a valid household `Session` cookie hitting `/api/operator/*` gets 401/403, never operator data
  - [ ] Regression test: a valid `OperatorSession` cookie hitting any `/api/*` household route gets 401/403, never household data
  - [ ] `POST /api/operator/login` rate-limited the same way as `/auth/login` (5 per 5 min, IP+email keyed)
  - [ ] `npm run typecheck -w apps/api` and `npm test -w apps/api` pass

### Phase 4: Operator frontend
- **Goal**: `/betrieb` renders live metrics behind its own login, fully outside the household-scoped app shell.
- **Files**: `operatorClient.ts`, `operatorHooks.ts`, `operatorTypes.ts`, `OperatorLoginPage.tsx`, `OperatorDashboardPage.tsx`, `router.tsx`
- **Dependencies**: Phase 3 (needs the real API, no mock parallel per CLAUDE.md §Phase 4)
- **End Conditions**:
  - [ ] `/betrieb` reachable without any household selection or `useActiveHousehold`-style state
  - [ ] Login → dashboard → logout flow works against the real backend in a manual browser check
  - [ ] `npm run typecheck -w apps/web` passes; existing web test suite unaffected

### Phase 5: Documentation
- **Goal**: an operator can be bootstrapped and understood from the README alone.
- **Files**: `README.md`
- **Dependencies**: Phase 4
- **End Conditions**:
  - [ ] New "Operator-Dashboard" section documents `create-operator`, the `/betrieb` login URL, and explicitly states this identity is separate from any household account
  - [ ] Full local run-through (`npm run create-operator` → log in at `/betrieb` → see real numbers) succeeds

## Phase Dependency Graph

```
Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5
```

Strictly linear — each phase's end condition is a precondition for the next (schema before identity code, identity before routes, routes before frontend, working feature before docs). Not fleet-parallelizable without artificial risk: Phase 3's isolation test needs both auth systems (Phase 2) *and* real routes to test against.

## Risk Register

1. **Regression in existing functionality**: new models/routes are additive, but `server.ts` and `router.tsx` are shared files. Mitigation: Phase 0 baseline + every later phase's end condition re-runs the full existing test suite, not just new tests.
2. **The isolation guarantee silently breaks in a future refactor** (e.g., someone later "simplifies" by merging `context.ts` and `operatorContext.ts`): Mitigation — `operator-isolation.test.ts` is a permanent regression guard, and the Key Decision above documents *why* the files must stay separate, for the next person tempted to merge them.
3. **CSRF/cookie confusion in the browser** if a developer manually mixes `client.ts` and `operatorClient.ts` calls in one component: Mitigation — the two clients live in clearly separate files (`operatorClient.ts` vs `client.ts`) and `OperatorDashboardPage` never imports from `apps/web/src/api/hooks.ts`.
4. **`create-operator.ts` run against a database mid-migration** (partial schema): Mitigation — same as `create-admin.ts` today, no new risk introduced; not re-solved here.

## Deployment Strategy

No new deployment surface — same Docker Compose / single-process deploy as the rest of the app (CLAUDE.md §30). `npm run create-operator` runs the same way `npm run create-admin` already does post-deploy. No new environment variables (Key Decision: reused `SESSION_SECRET`).
