# Campaign: PWA (Installability)

Status: completed
Started: 2026-08-30T23:58:30Z
Completed: 2026-08-31T00:25:00Z
Direction: Turn the existing SPA into an installable PWA — web app manifest, real icon assets, a service worker that precaches the app shell and never staleness-risks live game state, and a lightweight install prompt. Confirmed by reading the real repo before writing this campaign: `apps/web` has no `public/` directory, `index.html` has no manifest/icon links, and neither `vite-plugin-pwa` nor any hand-rolled service worker exists anywhere.

Session cap: 3 (novice trust level). Larger than the last two campaigns — new dependency, real (if simple) visual asset generation, and a deployment-config touch (nginx cache headers for the service worker file) — but still expected to fit in 1-2 sessions.

## Scope decisions made before phases were written

- **Offline strategy: app-shell only, not live data.** This app's core mechanic is shared, time-sensitive household state (task values escalate, assignments expire, buyouts race) — caching API responses for offline use risks a member acting on stale data (volunteering for a task someone already took, seeing a wrong point balance). The service worker precaches the static app shell (JS/CSS/fonts) so the app *launches* offline or on a flaky connection, but every `/api/*` call stays network-only (network-first, no fallback cache) — installability and fast repeat loads, not offline data editing. This is the standard, safe interpretation of "PWA-fähig" for a live multi-user app; full offline sync was never in CLAUDE.md's scope.
- **Tooling: `vite-plugin-pwa`.** New dependency, chosen over hand-rolling a service worker — it's the standard, actively-maintained Vite integration (wraps Workbox), generates the manifest link and SW registration automatically, and its dev-mode support means the SW can be verified without a full production build every iteration. Justified because no existing service-worker/PWA tooling exists to extend instead.
- **Icons: a simple generated placeholder, not final branding.** No logo/brand asset exists anywhere in the repo. Rather than block on branding work or invent something elaborate, the icon is a plain rounded-square in the app's own accent color (`#2b3fa0`, `packages/shared`... actually `apps/web/src/styles/tokens.css`) with a bold white "H" monogram — generated by rendering a small HTML/CSS file in a real browser and screenshotting it at each required size (192/512/maskable/apple-touch-icon/favicon), since no image-generation tool is available. Documented here explicitly as a placeholder the user can swap for real branding later; functionally correct (installable, passes manifest icon requirements) either way.
- **Update strategy: `autoUpdate`.** vite-plugin-pwa's `registerType: 'autoUpdate'` — the SW updates itself silently on next load rather than requiring a custom "new version available, reload?" UI. Simpler, and acceptable because this app has no risk of losing unsaved local state on a silent reload (no offline drafts, no client-only state that isn't already server-backed).

## Decision Log

(see "Scope decisions made before phases were written" above for the load-bearing pre-execution decisions)

- 2026-08-30: First icon-asset generation attempt used the browser's `take_screenshot` tool against a fixed-size HTML/CSS page — produced 640×643px output instead of the requested 512×512 (DPI/browser-chrome interference), unusable. Switched to `evaluate_script` rendering an SVG onto an exact-dimension `<canvas>` and reading back `toDataURL()` — this is resolution-independent and pixel-exact regardless of viewport/DPI quirks. Correct approach going forward for any future asset generation in this project.
- 2026-08-30: First attempt at saving that base64 output involved manually copying the tool's returned string into a `Write` call — silently truncated (7000+ chars down to ~1100), producing a PNG whose IHDR header was still technically valid (so a naive "does it decode" check passed) but whose image data was corrupt/unrenderable. Caught only by actually viewing the file with the `Read` tool's image support, not by parsing metadata. Switched to `evaluate_script`'s own `filePath` parameter so the tool writes the full output directly to disk — no manual transcription of large payloads through the conversation again.
- 2026-08-30: Phase 4's live verification ran against a real rebuilt Docker image (`docker compose build web && docker compose up -d web`), not just `vite preview` — this is what caught two real nginx bugs the dev-mode checks couldn't: `manifest.webmanifest` served as `application/octet-stream` (nginx has no default MIME mapping for `.webmanifest`) and, before any config was added at all, no cache headers whatsoever on any file. Both fixed and re-verified with `curl -I` against the running container. Also produced the single most convincing verification signal of the whole campaign: Chrome fired a genuine, unprompted `beforeinstallprompt` against the real deployment (not a synthetic test event), and the `InstallPrompt` component handled it correctly end-to-end. The actual native install was deliberately not triggered during verification (would have added a real app shortcut to the operator's machine) — the dismiss path was exercised instead, and the test-induced `localStorage` dismissal flag was cleared afterward so it doesn't affect the user's own first real encounter with the banner.
- 2026-08-30: Phase 3's build re-showed the exact same stale-precache symptom Phase 2 had supposedly fixed (`emptyOutDir: true` notwithstanding) — 10 precache entries with two old JS/CSS hashes alongside the current ones. Root-caused properly this time: this session's various `WEB_PORT=5173 npm run dev` background tasks (one per campaign's live-verification step — Phase 3 and 4 of the admin-onboarding campaign, the fairness-explanation campaign, and this one's own earlier `vite preview`) were each stopped via the `TaskStop` tool, which reported success every time, but the underlying process tree (bash → npx/cmd → node → vite) survived regardless — confirmed via `Get-CimInstance Win32_Process`, which found 4 orphaned bare `vite.js` dev-server processes (one per prior campaign, timestamped to match) plus a live `vite preview --port 4173` tree, all still running and holding handles into `apps/web/`. This is a **tooling gap worth knowing about, not just an artifact of this campaign**: `TaskStop` does not reliably kill the full process tree of a backgrounded `npm run <script>` command on this Windows environment. Practical mitigation used here: `Get-CimInstance Win32_Process | Where-Object CommandLine -match ...` to find real survivors (process-name filters like `Get-Process -Name esbuild` miss cmd.exe/bash.exe wrapper layers), then `Stop-Process -Force` each one, scoped tightly to processes whose command line unambiguously ties them to this project's own path or a command this session issued — never touching unrelated processes on the machine. `emptyOutDir: true` (added in Phase 2) is still the correct config and remains in place; it just cannot overcome a live process holding a file handle, which is a separate problem it was never meant to solve.
- 2026-08-30: Phase 2 quality spot-check on the first build caught `manifest.webmanifest` defaulting to `"lang":"en"` even though the whole app is German (`index.html`'s own `lang="de"`, every string in the app) — `vite-plugin-pwa` doesn't infer `lang` from anywhere, it just defaults to `'en'` unless set explicitly. Added `lang: 'de'` to the manifest config.
- 2026-08-30: The first build's precache manifest reported "21 entries (4034 KiB)" — far too many for a single-chunk SPA. Investigated: `apps/web/dist/` had been silently accumulating every build's hashed output since the start of this session (dozens of stale `index-*.js`/`.css` files dating back hours) instead of being cleared between builds, despite Vite's documented default of emptying an in-root `outDir`. Root cause: four orphaned `esbuild` helper processes (Windows leftovers from earlier `vite build`/`vite dev` invocations this session, tied to this project's own `node_modules` path) were holding file handles that silently defeated `emptyOutDir`. Fixed two ways: (1) terminated the orphaned processes and cleared the stale `dist/`, dropping the precache to the correct 8 entries (573 KiB); (2) set `build.emptyOutDir: true` explicitly in `vite.config.ts` rather than relying on the implicit default, so this can't silently regress again. This bug existed before this campaign (every previous session's builds were affected) but only became *consequential* here — a stray extra JS chunk in `dist/` was harmless noise before; once a service worker started precaching everything in `dist/`, it became real bloat shipped to every installed client.
- 2026-08-30: Live-browser check surfaced a real (if minor) Chrome deprecation warning: `apple-mobile-web-app-capable` alone is deprecated in favor of the standard, non-prefixed `mobile-web-app-capable` meta tag Chrome/Android now expects — Safari/iOS still wants its own prefixed version. Added both rather than replacing one with the other.
- 2026-08-30: Deferred `manifest.webmanifest` generation from Phase 1 to Phase 2. `vite-plugin-pwa` generates the manifest file and injects its `<link rel="manifest">` tag automatically from a config object — writing one by hand in Phase 1 would just be replaced when the plugin is wired up in Phase 2, so Phase 1's actual scope narrowed to icons + the index.html tags that are always manual regardless of the plugin (favicon, apple-touch-icon, apple-mobile-web-app meta).
